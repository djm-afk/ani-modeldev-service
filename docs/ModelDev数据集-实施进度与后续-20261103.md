## 三、必须知道的偏差与遗留问题

### 3.1 设计文档里的 NUL 分隔在 PostgreSQL 不可实现

设计附录 A.7 定义目标提交锁键为 `SHA256("ani.modeldev.dataset-target-commit.v1" + NUL + tenant_uuid + NUL + cluster_uuid)`。

**实际情况**：PostgreSQL 的 `text` 类型不允许 NUL，`chr(0)` 直接报 `null character not permitted`。

**处理**：改用 `bytea` 拼接（`convert_to(prefix,'UTF8') || decode('00','hex') || ...`），哈希的**字节串与设计完全一致**，只是绕过了 text 类型的限制。实测键值 `3561915907020135758`，与 Go 侧 `DatasetTargetCommitLockKey` 逐位相同，并有固定向量测试守护。

**需要你确认**：是否要把这条实现方式补写进设计附录 A.7（我没有擅自改设计文档）。

### 3.2 `make verify` 全量在 1CPU 测试容器下有并行超时

**现象**：`with-test-postgres.py make verify` 全量并行时，2 个测试失败：

- `internal/server/commandtest`：`TestGovernanceAcceptRejectsInvalidWireBeforePersistence` 的 3 个子例（`accepted_time_is_zero`、`accepted_time_loses_microsecond_precision`、`nested_deadline_loses_microsecond_precision`）报 `DeadlineExceeded`
- `internal/data/lifecycle`：`TestFinetuningStepBudgetAndResultAreOriginalAcrossReconnect` 报 `PIPELINE_DISPATCH_BLOCKED`

**证据表明是环境容量而非逻辑回归**：

- 两个包**单独跑**：`commandtest` 连续 3 次全过（~3.0–3.4 秒，该测试总预算 20 秒）；`lifecycle` 连续 2 次全过（~2.3 秒）
- `go test -p 1 ./...`：**0 失败 / 38 包**
- 容器限额是 CI 保真值 `--cpus=1 --memory=512m --tmpfs 384m`，未修改

**原因**：新增 7 张表（含复杂 CHECK 与 DEFERRABLE FK 环）使每次建 schema 略慢；并行跑多个包的 schema 时在单核容器里互相拖慢，撞上该测试 20 秒的**总**预算（而非单子例预算）。

**已按你的决定处理**：不改容器限额、不改测试超时，如实记录。**这意味着本分支合入后，CI 的 `make verify` 可能间歇性红。** 若你希望根治，可选方案是给该测试改为每子例独立超时（涉及改既有测试，需你另行授权）。

### 3.3 我引入并已修复的一个回归

`recordVerifiedInput` 重构时，我在 REJECTED 分支写成返回空 `InputVersion{}`，破坏了「迟到 proof 返回原终态」的语义（`TestInputTerminalFactsSurviveLateValidationOutcomes/REJECTED` 变红）。

已改为返回 `version, err`（保留原始终态行），修复后单跑与全量均通过。记录在此以免后续重构重犯。

### 3.4 枚举数量的偏差

设计 §14.2 把 `IDEMPOTENCY_CONFLICT` 列为新增 reason，但该值 **=5 早已存在**。本轮只新增 `INPUT_KIND_FORMAT_MISMATCH = 39`，未重复造码。P3 全量登记时同样不应重复。

### 3.5 C3 期间发现并修复的三个真实缺陷

这三个都是写代码时自查或测试发现的既有路径错误，不是本轮新引入的设计问题；记录以免复现。

| # | 缺陷 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | importer 暂存文件以 `O_WRONLY` 打开后又回读上传 | 每次上传都送 0 字节，且 `SizeBytes` 与实际不符，等于静默产出空文件 | 改 `O_RDWR`；测试锁定「上传字节数 == 暂存字节数」 |
| 2 | dataset 控制面被加入工作负载策略的通用受信更新名单 | 它能改写训练工作负载的 spec，超出「只拥有 importer 对象」的边界 | 从通用 updaters 中显式排除，仅当其对象带 importer 用途标签时放行；新增隔离断言 |
| 3 | dataset 控制面出现在 CREATE 允许名单中时未限制对象形状 | 它可以创建任意带 owner 标签的裸 Job，绕过 importer 用途约束 | CREATE 分支追加限制：该身份只能创建 importer 形状的 Job |
