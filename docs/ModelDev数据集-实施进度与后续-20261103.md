### 2.10 维护 gate 覆盖导入/重试/Ensure（2026-11-04 完成）

设计 §17.2 步骤 1 要求把新增导入/重试与 Ensure 接入与训练创建同一个维护 gate。
`ANI_MODELDEV_CREATE_PAUSED` 现在同时约束：

| 入口 | 是否受 gate | 返回值 |
| --- | --- | --- |
| 训练创建 `CreateExecution` | 是（原有） | `503 MODELDEV_CREATE_MAINTENANCE` |
| 环境 `EnsureTenantExecutionEnvironment` | **是（新增）** | `503 MODELDEV_MAINTENANCE` |
| Dataset 创建 / 导入 / 重试 | **是（新增）** | `503 MODELDEV_MAINTENANCE` |
| Dataset 查询、取消、归档/恢复 | 否 | 正常 |

实现上把 gate 收进 `modelDevDatasetScope`，顺序与 `CreateExecution` 一致：
**身份 → gate → 依赖检查 → 当前授权 → 租户映射**。三条理由写在代码注释里：
暂停期间不向未认证调用方泄露部署状态；不为一堆被拒请求各花一个数据库事务；
拒绝原因必须是「暂停」而不是笼统的依赖不可用。

**测试**：`service/modeldev_dataset_maintenance_test.go`

- create/import/retry 在暂停时都返回 `MODELDEV_MAINTENANCE`；
- cancel 与查询**不**返回该 reason（保持可达）；
- 未认证调用返回 401 而不是泄露暂停状态；
- 授权失败时 gate 槽位会被释放（连续 5 次失败后 `pauseAndDrain` 仍能不超时完成），
  否则一次拒绝风暴会让维护排空永远等不到。

### 3.1 设计文档里的 NUL 分隔在 PostgreSQL 不可实现

设计附录 A.7 定义目标提交锁键为 `SHA256("ani.modeldev.dataset-target-commit.v1" + NUL + tenant_uuid + NUL + cluster_uuid)`。

**实际情况**：PostgreSQL 的 `text` 类型不允许 NUL，`chr(0)` 直接报 `null character not permitted`。

**处理**：改用 `bytea` 拼接（`convert_to(prefix,'UTF8') || decode('00','hex') || ...`），哈希的**字节串与设计完全一致**，只是绕过了 text 类型的限制。实测键值 `3561915907020135758`，与 Go 侧 `DatasetTargetCommitLockKey` 逐位相同，并有固定向量测试守护。

**处置结论（2026-11-04 确认）**：设计附录 A.7 的 `NUL` 是**字节串语义**，不是要求 PostgreSQL 的 `text` 字面量含 NUL。实现按字节串实现即满足合同，无需改设计文档；此处记录实现方式，供后续复核者不必重查。

### 3.14 导入 503 的根因：target_snapshot 的 input_scope 必须是嵌套对象（2026-11-04 定位并修复）

**结论**：503 与 receipt/task 的写入函数无关，是 `biz.DatasetImportTarget.Canonical()` 产出的 JSON 形状与数据库 CHECK 不一致。

| 项 | 事实 |
| --- | --- |
| 缺陷 | `Canonical()` 输出**扁平点号键**：`"input_scope.bucket"`、`"input_scope.approved_prefix"` 等 |
| 合同要求 | 设计 §7.4 与迁移 CHECK `modeldev_dataset_import_tasks_check5` 都要求 `input_scope` 是**嵌套对象**（`jsonb_build_object(...)`） |
| 后果 | 扁平形式序列化完全正常、单测全绿，但 `target_snapshot = jsonb_build_object(...)` 恒为 false → 每次受理必然 `23514` → 数据层包成 `ErrPersistence` → 503 |
| 为何没被单测发现 | 没有任何用例断言过 canonical 的**字节形状**，只断言摘要稳定与变化敏感 |

**实测证据（真实库 `ani_modeldev_v21`）**：

1. 扁平形式插入在事务内立即失败，报 `violates check constraint "modeldev_dataset_import_tasks_check5"`；
2. 同样数据把 `input_scope` 改为嵌套对象后 `INSERT 0 1` 成功；
3. 用 `pg_get_constraintdef` 确认 `check5` 正是 `target_snapshot = jsonb_build_object(...)`；
4. 修复后用 Go 真实产出的 canonical 字节，以 `modeldev_v21_runtime` 角色跑完整受理链路（目标提交锁 → 输入身份锁 → 版本序号 → task → receipt → operation）全部成功。

**修复**：`Canonical()` 改为嵌套对象并用 `json.Encoder`（`SetEscapeHTML(false)`）输出，顺带消除手工字符串拼接；同时增加三项回归：

- `TestDatasetImportTargetCanonicalShape`：断言**逐字节**固定向量与「摘要 == 该字节的 SHA-256」；
- `TestDatasetImportTargetCanonicalRejectsForeignNamespace`：非标准 Namespace 名或零 UID 直接拒绝（避免钉住一个无人校验的身份）；
- canonical 前置校验扩展到 `ClusterID`/`NamespaceUID` 必须是规范 UUID。

**顺带**：`internal/data/dataset/imports.go` 中受理/发布/状态迁移路径上的裸 `biz.ErrPersistence` 全部补成 `fmt.Errorf("%w: …: %v", …)`，保留数据库码与约束名。这类包装正是本轮定位耗时的直接原因，后续同类问题可直接从错误文本读到 `23514` 与约束名。

### 3.15 迁移已回灌 owner 与最小权限（2026-11-04）

`0004_dataset_domain.up.sql` 末尾新增受角色存在性保护的授权块：

- 7 张表与 2 个锁函数 `OWNER TO modeldev_v21_migrate`；
- `modeldev_v21_runtime` 获得 7 表 `SELECT/INSERT`，仅 `modeldev_datasets`（8 列）、`modeldev_dataset_import_tasks`（27 列）、`modeldev_dataset_import_attempts`（20 列）、`modeldev_dataset_credential_issuances`（10 列）获得**列级** `UPDATE`，全程无 `DELETE`；

实测：在隔离 schema 中模拟「现场已存在表级 UPDATE」的状态后执行，结果表级 UPDATE 被清除、只剩预期列级权限、函数 owner 与 EXECUTE 正确；随后在生产库事务内执行同一块（已提交），并使 3 张既有表之外的 7 张数据集表全部回到 `modeldev_v21_migrate`。

### 3.18 准入策略更新引发过一次全集群回归（已修复，重要教训）

按「现在就装」的决定，用 `render.py` 重新渲染并 `kubectl apply` 了三个 `ValidatingAdmissionPolicy`。结果**全集群 Pod/Job 创建被拒绝**：

```
ValidatingAdmissionPolicy 'modeldev-workload-guard-v1' denied request:
  composited variable "protected" fails to evaluate: no such key: metadata
```

**根因（两次修正后才定位，记录以防再犯）**：

之前的判断「缺少 `namespaceSelector`/`objectSelector`」**不成立**——补上空 selector 后重新应用，错误完全不变。
真正的根因是 `import_pods()` 生成的两个 dataset 分支缺少空对象守卫：

```cel
// 错误：CREATE 时 oldObject 不存在，oldObject.metadata 求值即报 no such key
(has(oldObject.metadata.labels) && "modeldev.ani.io/purpose" in oldObject.metadata.labels && ...)
```

`protected` 变量把这段裸拼在末尾，`failurePolicy: Fail` 把求值错误变成拒绝，于是**所有**工作负载请求被拒，
与标签无关。修复为 `(obj != null && has(obj.metadata.labels) && ...)`。

**被掩盖的第二个缺陷**：`test_render.py` 里有一行
`self.assertNotIn("namespaceSelector", policy["spec"]["matchConstraints"])`——它把 bug 写成了断言，
所以门禁一直绿。已改为断言空 selector 必须**存在**，并新增 `test_every_import_pods_read_is_null_guarded`
锁住 null 守卫。

**影响与处置**：ModelDev 自身 Pod、普通业务 Pod、`ani-service-mtls-reload` CronJob 全部无法创建。
第一次已从 `.tmp/rollback/policies-before-dataset-worker/` 回滚恢复；修复后重新安装成功（见 §3.18.1）。

**教训（供后续复核）**：
1. `kubectl apply --dry-run=server` **不会**验证 CEL 运行时对真实对象的求值，只有真实创建才会暴露；
   更新这类全局策略后必须立刻用一个真实 Pod 做冒烟。
2. 渲染器输出不能假设与线上逐字段同形；应用前应对 `matchConstraints` 做结构对比，而不仅是语义比较。
3. 回滚备份要在 apply 之前取，并保留 `resourceVersion` 的更新方法（备份的 rv 会过期）。
4. **测试断言也可以固化 bug**：看到 `assertNotIn` 断言某个「看起来像无关字段」时，先问它为什么存在。
5. 修完一个疑似根因后必须重测原症状；本次第一次修复后症状未变，才继续找到真因。

4. RustFS 日志给出权威原因：
   ```
   "event":"s3_authorization_denied","reason":"no_policy_allows_action",
   "action":"S3Action(PutObjectAction)","bucket":"ani-md-v21-input-01a15f47",
   "account":"mdv21-01a15f47-sts-73c98d19","is_owner":false
   ```
   注意 `account` 带 `-sts-` 后缀：**父凭据本身就是一个 STS 会话身份**，而不是长效 key。
5. 直接调 `AssumeRole` 返回 **200**，会话签出成功；解码 SessionToken 内的 `sessionPolicy`：
   ```json
   {"Version":"2012-10-17","Statement":[{"Effect":"Allow","Action":["s3:PutObject","s3:GetObject"],
     "Resource":["arn:ats:s3:::ani-md-v21-input-01a15f47/inputs/<tenant>/*"]}]}
   ```
   `parent` 字段 = `mdv21-01a15f47-sts-73c98d19`。

**判断**：RustFS 对「STS 会话再 AssumeRole」的授权是**父会话权限与新策略的交集**。父会话没有
`input bucket` 的 PutObject，交集为空，因此无论内联策略怎么写都 403。`arn:` 被规范化成 `arn:ats:`
是 RustFS 的内部形式，不是原因。

**这不是代码问题**：应用侧能做的（会话名、动作集合、资源前缀、去探测）都已试过且无效。

**需要基础设施侧（RustFS IAM）二选一**：
1. 给 `mdv21-01a15f47` 这个身份在其 **自身 policy** 上授予 `input bucket` 的 `s3:PutObject`
   （以及 `GetObject`，供验证阶段回读），再由数据集会话做交集收敛；
2. 改用**长效访问密钥**作为 `modeldev-runtime-issuer` 父凭据（当前挂载的是一个 sts 会话凭据），
   这样 AssumeRole 的内联策略才是上界而不是交集。

**现状**：19 条任务全部 `FAILED`（调试过程累积），槽位已清空；代码与镜像均已就绪，

### 3.25 真实 Alpaca 语料的三个合同缺口（已按用户决定的 A2 处理）

| 合同约束 | 源码位置 | 处理 |
| --- | --- | --- |
| 只接受 `.json` 后缀 | `internal/biz/dataset_source.go` `ValidateSourceFilePath` | 放宽为 `.json` **或** `.jsonl`（不嗅探格式，仍按扩展名） |

“同一字段两种拼写”判为冲突，而是按英文优先取值。`_zh` 值仅在该字段无英文拼写时使用。

**偏离设计**：设计 §96 明确「本期不做…字段映射」。A2 让 `_zh` 参与取值，实质引入了**固定别名映射**
（只三种键名，不做任意字段名重写）。用户已确认接受；后续若合入上游，应在设计文档中补一句说明。

**顺带修的两处**：
1. importer 的 `HTTPFetcher` 原本拒绝一切重定向，而 ModelScope 的 LFS 文件必然 302 到 CDN。
   改为**主机白名单**：仅允许两家 Hub 自身的 CDN 主机、仅 https、拒绝 userinfo 与显式端口、最多 2 跳。
2. 预览写入 `preview jsonb`（CHECK 要求 `object`）时不能直接塞 JSONL 原始字节，改为按设计 §11.1
   构造结构化预览对象。

#### 3. 两个真实缺陷

**（a）`DecodeSourceSnapshot` 丢弃 `resolved_at`**

`internal/biz/dataset_import_plan.go` 只解析了 selection 字段，`resolved_at` 被丢弃。后果：版本视图 `source.resolved_at` 报 `0001-01-01T00:00:00Z`，且 `snapshot_sha256` 与受理时算出的不同（该字段属于冻结快照身份）。已补解析并校验微秒精度。

**（b）Gov 把 revision 冲突降级成 503**

ModelDev 按设计用 `Aborted` 承载 `COMMAND_CONFLICT`（revision 过期），用 `AlreadyExists` 承载重名。Gov 数据层把该 reason 硬绑定到 `AlreadyExists`，`Aborted` 被判合同违约 → 降级 `503 MODELDEV_DATASET_UNAVAILABLE`，前端拿不到 409。

改为「每个 reason 允许一组 code」，`COMMAND_CONFLICT` 同时接受两者；其余 reason 仍单一 code，不匹配照旧降级。补 `modeldev_dataset_client_test.go` 两条用例（两种 code 均穿透；错配对仍拒绝）。

实测：过期 revision → `409 COMMAND_CONFLICT`，重名 → `409 COMMAND_CONFLICT`，正确 revision → `200`。
