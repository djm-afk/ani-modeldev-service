# 领域文档

整个服务共用一套领域文档：根目录的 `CONTEXT.md` 保存业务术语表，
`docs/adr/` 保存架构决策记录，也就是 ADR。

## 查看代码前

- 如果根目录的 `CONTEXT.md` 已存在，先阅读其中已经明确的业务术语。
- 阅读 `docs/adr/` 下与当前工作有关的架构决策。
- 继续遵守根目录 [AGENTS.md](../../AGENTS.md) 中的服务分层边界和验证要求。

如果术语表或架构决策文档尚不存在，直接继续工作，不必专门提醒缺失，
也不应提前创建空白占位文件或建议先建空文档。
`/grill-with-docs` 和 `/improve-codebase-architecture` 会使用
`/domain-modeling`，在业务术语或决策真正明确后创建这些文档。

## 文件布局

- `CONTEXT.md`：整个服务共享的业务术语表，有实际内容时再创建。
- `docs/adr/NNNN-<decision>.md`：已经明确的架构决策。
- `cmd/`：服务的组装入口，负责把各个组件连接起来。
- `internal/`：现有的入站适配、业务领域、数据适配和服务器相关代码。

## 沿用术语表中的用词

任务标题、设计讨论、假设、测试和代码中的业务概念，使用 `CONTEXT.md`
已经确定的名称。不要改用术语表明确排除的同义词。
如果某个概念还没有定义，先判断它是否属于本服务，
或者把这项缺口记录下来，交给 `/domain-modeling` 澄清。

## 明确指出与既有决策的冲突

如果一个方案与已有 ADR 冲突，应写明该决策的名称和链接，
解释为什么可能需要重新讨论，不能悄悄覆盖原来的决策。
