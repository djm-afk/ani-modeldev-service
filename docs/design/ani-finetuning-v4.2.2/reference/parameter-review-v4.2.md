# ANI 微调 v4.1：面向下一阶段参数开放的评审要点

评审日期：2026-10-14。性质：计划评审；不是实施或验收结果。

## 依据与范围

直接依据本次上传的《ANI-CPU受管微调-v4.1-完整计划与复核包(1).zip》。已阅读包内完整 spec.md、W0–W6、验收计划、变更和自复核；规范 SHA256：`4c8430fc90ed92671ad06120113a909030ee76d70f807074790c5633f0b0de77`。另读取 ModelDev 主分支实际返回的固定提交 `c5fd93c60f4aa6af229ef39d3cc503396f6d0ffb` 的参数相关源码，不将该提交与包内较早代码评审基线混为一谈。没有修改原包、GitHub或集群，没有运行Fedora负载/业务测试。

## 结论

作为固定配方的 CPU 微调闭环，现有主架构可继续；作为“下一阶段可以方便、安全地开放更多参数”的实施准备，仍需补参数层职责、版本/兼容范围、预设与执行展示、训练实际消费和相应验收。不是推翻骨架，也不是要求当前立即开放全部参数。

v4.1只修订启动/停止仲裁、指标生成责任和完成标准分层；A02/A07/D02仍仅开放learning_rate/max_steps，D06固定rank8/alpha16/cutoff128/batch1/accumulation1。按当前任务完整实现，仍会交付一个受限微调预设，而非较丰富调参工作台。

## 必须在W1合同定稿前补齐

### P-01 规则归属和版本边界

定位：A02、A07、D02、D05、W1。

公共校验保留结构、类型、存在性、数字词法、重复键、大小限制；受管程序合同定义支持字段及执行映射；不可变Release定义当前批准的默认值、范围/枚举、固定值和必要组合限制；执行快照保存合并后的实际参数。未知字段仍拒绝，不能以扩展为由直接透传任意框架参数。

当前两字段是当前微调合同的能力，不是整个FINETUNING永久只能两个字段。明确参数定义的单一维护位置，可复用现有ParameterContractVersion/ParameterRule等结构；不新增参数服务、插件注册中心或规则语言。保留typed finetuning结构也可以，不要求改成任意map。

### P-02 兼容要求限定对象

定位：A07第217行、D05第478行、FT30及W1/W6。

旧CPU合同、旧快照、原键重放保持旧含义；新增参数能力按明确的新合同/Release启用。不把“旧拒绝集不变”解释为所有未来通用训练永久拒绝新合法值。不能只是原地放宽旧规范并宣称兼容，也不需要两套服务。

新字段需要相应API/codec和程序适配是正常扩展；已支持字段的范围扩展可发布新Release；用户在已批准范围内选择不同数值不需要每个数值一份Release。公共解码在Release解析前的旧限制也必须有明确版本/能力分流，不能只改后端Release规则。

### P-03 前端规则和执行展示

定位：D02、D05、D09、D12/W1。

沿用前端读取预设的做法。创建页使用当前可选Release的规则与默认/固定值；详情页使用原执行冻结配置；实际训练步数来自运行事实。后端只投影允许公开的字段，不返回完整内部快照/凭据。多个Release聚合不能用任意首个Release的规则代表当前生效版本；切版期间按已声明的受理规则处理，并明确返回实际解析结果。

源码提醒：`internal/service/materials.go` 的 `parameterView` 对INTEGER不读取Value，而是epochs返回3、其他返回64。这对当前受限CPU输入成立；未来微调max_steps、rank或可变batch不能直接沿用。W1应明确类型解析、范围检查、错误返回和规则投影，不在前端补一个常量掩盖后端错误。

## 随W0/W3/W4实现的必要约束

### P-04 配方覆盖和实际消费

定位：D05、D06.1、W0/W1/W3。

完整支持链：用户显式值→当前合同校验→Release补默认值/固定值→原执行快照→entry最终配置/argv→真实框架消费→安全配置摘要与运行事实。

固定字段不可由用户覆盖；已批准用户值不得被镜像内默认配方覆盖；执行期间不读取最新Release。可运行时生成固定格式配置文件，不等于开放用户任意YAML。保存安全的最终配置或确定的配置摘要；不要建立第二份独立参数权威。

### P-05 范围、组合、资源与文件合同

定位：A07、D06、D07、D10、D13。

维持CPU单节点、固定基模、JSON和原流水线；后续普通超参数开放不自动扩大GPU/任意脚本/新框架范围。

对batch、梯度累积、cutoff、rank等新增可调项明确独立值与组合限制，并验证实际预算；不继承20步固定配方的容量保证。训练长度选择max_steps或epochs时明确优先级/互斥；alpha独立还是从rank派生需要固定规则，不能动态隐含改变旧执行。

文件真实摘要始终是运行事实；RequiredFiles维护获准文件结构和上限，不把基准产物SHA或字节数变成所有参数组合必须相同。文件集不变的参数变化不必每个取值重建Pipeline；实际输出结构改变时再发布相应新合同。

## W6增加的参数验收（建议，不声称现有已包含）

1. 预设规则、默认/固定值和后端实际接受集合一致；整数不同于3/64仍准确展示。
2. 非默认合法值从BFF到快照、entry最终配置、真实负载保持一致；不能接受了但仍执行默认值。
3. 重复原请求不因默认值/范围更新改变旧任务；详情仍展示旧快照。
4. 新执行不同参数产生不同执行配置；未知/越界/非法组合在计算开始前拒绝。
5. 增加梯度累积、改变步数或其他候选参数时，实际optimizer_steps/metrics/summary语义正确，不以日志条数或请求值冒充实际步数。
6. 参数变化后的时间、内存、spool和输出上限以及失败/停止路径通过对应验证；无需穷举连续数值全部组合，但批准范围必须有代表性、边界与反例依据。

## 分工与时机

W1负责单一规则、版本/兼容、解析/快照、查询响应；W0负责真实配置消费和非默认负载；W3只精确传递冻结配置并复用截止/关闭；W4核对参数变化对文件与发布的真实影响；W6联动上述用例。W2继续既有JSON/READY语义，64条仍属于Release，不再写进导入器。W5的Model正式对接不应成为参数合同和负载验证的开工前置。

建议现在先修职责和公共投影，允许首发仍只批准learning_rate=0.0001、max_steps=20；下一阶段再明确批准少量新增字段和范围。不要为展示方便提前接受未实现字段，也不要为未来扩展先构建大平台。
