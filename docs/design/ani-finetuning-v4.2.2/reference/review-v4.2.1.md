## 2. R1：登记副作用的派发与停止，应明确共同仲裁

**分类：P1，实现前必须补齐；继承性合同空隙，不是本次 GPU 新增代码的已复现缺陷。**

位置：D08.3（约 L786–802）、D09.2（L833–841）、D09.3（L843–847）。

已写明的规则包括：第一次外部写入之前保存登记意图；new 分支先 CreateModel 再 CreateModelVersion；正常登记/恢复使用原记录和有限 lease/CAS；停止后不产生新的正常登记写入。问题是尚未明确“具体哪一次外部副作用已经进入在途”的提交点，与 stop/deadline 之间如何互斥。

登记意图已存在，不能等同于之后所有 RPC 都已在途；登记 worker 之间的 lease/CAS，也不自动等同于它与停止操作共同仲裁。

可能的错误实现顺序：

```text
CreateModel 已完成
→ 读取执行尚未停止，准备 CreateModelVersion
→ Stop 提交
→ 按此前读取结果新发 CreateModelVersion
```

这与 D09.3 的意图不一致，但本次没有证明现有实现已经发生这种竞态。

### 最小修改建议

在现有登记与执行记录中补齐以下规则，不增加通用许可系统或跨服务事务：

> 正常登记每个会产生外部副作用的具体操作，在取得本次派发资格时，必须与 stop/deadline 使用同一执行级数据库串行化边界或等价原子条件。事务内核对关闭状态、时限、原登记阶段/业务键及内容，并记录该具体操作进入在途；RPC 和对象 I/O 在事务外进行。只有登记意图存在，不代表后续尚未派发的步骤都已在途。
>
> 停止先提交则禁止新的正常派发；派发先获准则作为原在途操作处理，结果可迟到，按原键查证并保存收据。CreateModel 的迟到成功不授予尚未派发的 CreateModelVersion 执行权。不能承诺跨服务写入与本域 Stop 在物理时间上绝对原子。
>
> 已 CLOSED 后的用户显式原登记恢复继续遵守 D09.2 的当前权限和限定内容，不被误写成所有恢复永久禁止，也不允许借原恢复改变目标或启动计算。

原存储交接如果含实际写入，也应明确这些写入的在途归属；不用把只读查询或纯字段转换都新增为许可记录。已有等价字段足够时直接复用。

### 测试落点

补入 FT21/FT25 的原有测试，不另设平台级用例体系：

1. Stop 在首次具体派发仲裁前提交，外部写调用数为零。
2. CreateModel 已结束，Stop 在版本派发前提交，保留容器收据但不新发版本写入。
3. 版本派发先获准，随后 Stop 且响应丢失：保存/查证原结果，不换目标/key，不把迟到事实改成未发生。

修订责任：W4 与现有关闭机制负责人；真实 Model 侧维持原幂等和查证。W0/W1 等无关开发无需等待此项完成。
